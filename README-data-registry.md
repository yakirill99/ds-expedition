# Модуль: data-registry — регламент организаторов + локатор данных

Ветка `feat/data-registry` (base `develop`). Содержит официальные материалы
организаторов (вербатим, без правок) и безопасный локатор сырых данных.

## Состав

| Путь | Что это |
|------|---------|
| `vendor/organizers/compute_metrics.py` | Официальный расчёт Archaeology Assistive F1 (КОЗ-3). Работает standalone: при отсутствии `config.py` использует встроенные дефолты, совпадающие с платформенными (заявлено в шапке скрипта). |
| `vendor/organizers/data_structure.md` / `.yaml` | Официальная структура `public_dataset` (35 регионов `region_XXXX`, типы La/Ae/SpOr/Or/MagGr/EtGr/TerFl + UTM.json + extra). |
| `pyproject.toml` | `vendor` добавлен в `extend-exclude` ruff — организаторский код не должен падать под наш линт. |
| `scripts/locate_data.py` | Локатор данных (quick-режим по умолчанию). |
| `tests/test_locate_data.py` | 13 тестов локатора. |

## Локатор данных

Данные лежат на `/mnt/d` (Yandex.Disk, WSL drvfs/9P) и **докачиваются**.
Полный обход этого дерева (rglob/stat каждого файла) на фоне синхронизации
забивает диск — поэтому скрипт делает только плоские `os.scandir` глубины 2,
не читает содержимое файлов и не считает хэши.

```bash
# безопасно даже во время докачки (по умолчанию quick, без stat):
uv run python scripts/locate_data.py --expect-min 192

# после завершения докачки — один раз с размерами:
uv run python scripts/locate_data.py --expect-min 192 --full --json locate_report.json
```

Что проверяется: для каждого участка `NNN_*` — наличие `*.las|.laz` и `*.tif`
(по именам файлов, «действительное количество, а не список директорий»).
Участок «полный» = есть и las, и tif. Служебные папки (`layers`, `extra`,
`archive`, `current`) не открываются; zip-двойники в корне не считаются.
Коды возврата: 0 — ок; 2 — strict-недобор `--expect-min`; 130 — прервано
(частичный отчёт печатается). Прогресс — каждые 25 сайтов, `--timeout`
(по умолчанию 300 с) — мягкая остановка без ошибки.

## Метрика: чек-лист сверки пайплайна (по compute_metrics.py, koz3-1.5.0)

### Классы и веса (CLASS_WEIGHTS, сумма 100)

| Канонический ключ | Вес | Синонимы на входе |
|---|---|---|
| `kurgany_povrezhdennye` | **30** | курганы_поврежденные, курганы_разрушенные, поврежденные, разрушенные |
| `kurgany_tselye` | **20** | курганы, курганы_целые, целые |
| `gorodishcha` | 15 | городище, городища |
| `arkhitektury` | 10 | архитектура, архитектуры |
| `object_poly` | 10 | objectpoly, objectspoly (геофизика: полигональные аномалии) |
| `finds_points` | 10 | findspoints, findspoint (геофизика: точечные аномалии) |
| `fortifikatsii` | 5 | фортификация, фортификации |

Игнор-классы (выкидываются): `StructrPoly`, `StructPoly`, `StructurePoly`.
Вывод: **сумма 30+20+15+10+10+10+5 = 100**.

### Формулы и матчинг

- `precision = tp / (tp + 0.5*fp + ε)` — лишнее срабатывание штрафуется
  коэффициентом **0.5**; `recall = tp / (tp + fn + ε)`; ε = 1e-6.
- Матчинг one-to-one, **жадный по confidence** (сортировка по убыванию).
- GT-полигон (сценарий А): hit, если
  `cov = area(P∩G)/min(area(P),area(G)) >= 0.5` **и** представительная точка
  предсказания (`representative_point`) внутри GT.
- GT-точка (сценарий Б): расстояние центроид→точка **≤ 2.0 м**
  (предсказания-Point превращаются в круг r = 2.0 м, 32 вершины).
- Итог: взвешенное среднее F1 **по классам, присутствующим в GT** (веса
  нормируются на присутствующие; класс, есть в GT и F1=0, сохраняет полный вес).
- CRS: ожидается **EPSG:3857**, автоприведение к UTM (зона по центроиду)
  для площадей/расстояний (`INPUT_CRS_MODE=auto`).

### Лимиты приёмки (из конфига метрики)

- файл ≤ **100 МБ**, body ≤ 100 МБ;
- ≤ **20 000** фич на файл;
- ≤ **3000** вершин на полигон;
- справочные (не влияют на score): Boundary IoU, Hausdorff95, PoLiS,
  полнота/точность по типам данных (`markup_type`: la/li→лидар, ae→аэрофото,
  spor→спутник, or→ортофото, maggr/etgr/terfl→геофизика), размерные категории
  GT-полигонов (бины 100/500/1000/5000/10000 м²).

### Следствия для нашего экспорта GeoJSON

1. `class_name` — только канонические ключи из таблицы (тогда синонимы не нужны).
2. `confidence` заполнять осмысленно: им управляется жадный матчинг; пропуск = 1.0.
3. **Никаких MultiPolygon** — метрика берёт только наибольший полигон, хвосты
   теряются. Слитые объекты разбивать на отдельные features (совпадает с
   чейнджлогом: «один объект = один полигон в пределах одного типа данных»).
4. `region_name` = идентификатор участка (например `013_Нора_Виннон`),
   `sub_region_name` — при наличии; на score не влияют (pooling по классам
   через все источники), но нужны для отчётов платформы.
5. `markup_type` проставлять (la/li/…) — влияет только на справочные показатели.
6. CRS вывода — EPSG:3857 (совпадает с нашим экспортом), упрощение гарантирует
   ≤ 3000 вершин/полигон.
7. FP-штраф 0.5 — умеренный порог confidence предпочтительнее жёсткого;
   приоритет — полнота по курганам (веса 30+20 = половина метрики).

## Если скан/обход снова завис (без перезагрузки)

Windows PowerShell: `wsl --shutdown` — убивает WSL VM вместе с очередью 9P
запросов; потом `wsl` заново. На время работы с /mnt/d ставить синхронизацию
Yandex.Disk на паузу (иконка в трее).
