### Наше железо: RTX 5070 (12 ГБ)

- Пересчёт времени: **4090 ≈ в 1,6–1,8 раза быстрее**. Коэффициент замерить самим в первую неделю.
- Правило: **полный локальный прогон на 5070 ≤ 15 мин** → на платформе ~8–10 мин + запас на I/O.
- 12 ГБ VRAM ограничивает обучение сильнее, чем скорость: AMP, gradient checkpointing, небольшой batch.
- Blackwell: PyTorch с CUDA 12.8+. Старые сборки mmcv / spconv могут не работать.

## 1. Функциональное описание задачи

### 1.1. Что мы делаем по сути

Мы пишем программу, которая получает на вход геопривязанные данные съёмки участка местности и возвращает файл с координатами найденных археологических объектов. Никакого интерфейса и интерактивности на этапе испытаний не нужно: платформа запускает наш entrypoint, он читает папку с данными, пишет один выходной файл, платформа считает по нему метрику.

Архитектурно это классическая задача **семантической сегментации / детекции на аэрокосмических данных**, усложнённая тремя вещами:
1. данных несколько типов, они разной природы и разного разрешения (комплексирование — это и есть про их объединение);
2. часть объектов видна только в рельефе, часть — только в геофизике, часть — только на старых снимках;
3. выход не пиксельная маска, а **вектор в географических координатах**, и от способа его построения метрика зависит не меньше, чем от качества модели.

### 1.2. Вход

| Тип данных | Формат | Что физически содержит | Какие объекты видит |
|---|---|---|---|
| Воздушное лазерное сканирование | `.las` (облако точек) + `hillshade .tif` | XYZ + интенсивность, номер отражения, класс точки | Рельефные: курганы, валы, рвы, городища, дороги, террасы. Проникает сквозь растительность |
| Современная аэрофотосъёмка | `.tif` | RGB/мультиспектр высокого разрешения | Видимые на поверхности контуры, почвенные и растительные признаки |
| Историческая аэрофотосъёмка | `.tif` | ЧБ снимки прошлых лет | Объекты, уничтоженные распашкой или застройкой после съёмки |
| Спутниковая съёмка | `.tif` | Мультиспектр, широкий охват | Крупные структуры, сезонные признаки |
| Магнитометрия | `.tif` (значения + визуализации) | Аномалии магнитного поля | Печи, ямы, обожжённые и железосодержащие объекты, заполнения |
| Георадар | `.tif` (визуализации срезов) | Отражения на разных глубинах до 5 м | Фундаменты, погребения, подповерхностные конструкции |

Плюс **обучающая разметка** в GeoJSON (EPSG:3857):
- `Polygon` — крупные объекты с различимыми границами;
- `Point` — мелкие объекты и аномалии, где полигон недостоверен.

Все слои геопривязаны, но имеют разное разрешение, разный охват и могут отсутствовать на части территории. Совмещение слоёв — отдельная инженерная задача, а не «просто сложить каналы».

### 1.3. Выход

Один файл предсказаний в формате примера выходного файла с платформы: геометрии объектов в EPSG:3857. Ключевое следствие из регламента: **на выходе всегда полигоны**, даже для точечных объектов, потому что точечный GT засчитывается, если центр масс нашего полигона попал в радиус R_tolerance от GT-точки. Для аномалий достаточно небольшого круга/квадрата вокруг предсказанного центра.

### 1.4. Функциональные блоки (общие для всех стеков)

```
[1] Загрузка и инвентаризация данных
        ↓
[2] Препроцессинг
    2a. LAS → фильтрация земли → DTM/DSM
    2b. DTM → производные рельефа (hillshade, slope, SLRM, openness)
    2c. Приведение всех растров к общей сетке/CRS
    2d. Нарезка на тайлы с перекрытием
        ↓
[3] Модель(и): тайл → карта вероятностей / heatmap
        ↓
[4] Сборка тайлов обратно (blending, снятие краевых артефактов)
        ↓
[5] Векторизация: порог → контуры → полигоны в EPSG:3857
    + фильтр по площади, упрощение, контроль центра масс
        ↓
[6] Постобработка: удаление дублей (геометрический NMS), слияние по классам
        ↓
[7] Запись выходного GeoJSON
```

Отдельно, вне inference-пути:
- **[T] Обучение**: сплит по территориям (не случайный, иначе утечка через соседние тайлы), аугментации, лоссы под дисбаланс классов.
- **[V] Локальная метрика**: копия официального алгоритма расчёта (его дают на платформе) + свой валидационный набор. Без неё 3 сабмита в сутки сгорают вслепую.
- **[I] Обвязка инференса**: папка `inference/`, entrypoint, офлайн-режим, замер времени, контроль размера архива.

### 1.5. Чем стеки отличаются функционально

Блоки [1], [5], [6], [7], [V], [I] **одинаковы во всех трёх стеках**. Различия только в блоках [2]–[4]:

**Стек 1 — растровый baseline.**
Блок [2] сводит все модальности к одной растровой сетке и складывает их в каналы одного тензора: `[hillshade, slope, SLRM, openness, R, G, B, hist_pan, magnitude, gpr_slice, ...]`. Блок [3] — одна сеть энкодер-декодер, на выходе одна карта вероятностей (или N карт по числу классов объектов). Блок [4] тривиален.
*Одна сетка, один тензор, одна модель.*

**Стек 2 — модальные эксперты + фьюжн.**
Блок [2] выполняется отдельно для каждой физической группы данных, каждая остаётся в своём родном разрешении. Блок [3] — несколько независимых моделей: эксперт по рельефу, эксперт по оптике, эксперт по геофизике (последний может быть не сегментатором, а детектором центров — heatmap + локальные максимумы). Блок [4] дополняется **слоем фьюжна**: калибровка вероятностей каждого эксперта, приведение их к общей сетке, объединение (голосование / взвешенное среднее / мета-модель на признаках кандидатов).
*Несколько независимых веток, сходящихся в одной точке. Именно здесь живёт ручка баланса precision/recall.*

**Стек 3 — 3D + 2D.**
Блок [2] сохраняет облако точек как облако: вместо DTM формируются блоки точек с признаками (интенсивность, номер отражения, локальная геометрия), а 2D-разметка переносится на точки. Блок [3] распадается на две ветки: 3D-сеть по точкам (классификация точек или поиск аномалий) и обычная 2D-ветка. Блок [4] дополнительно **проецирует результат 3D-ветки в растр**, после чего объединяет его с 2D-веткой.
*Самая длинная цепочка: появляются перенос меток в 3D и обратная проекция в 2D — два новых источника ошибок.*

## 2. Сравнение стеков

### Стек 1. Растровый baseline (единая 2D-сегментация)

**Суть:** LAS → DTM → производные рельефа (hillshade, slope, SLRM, openness) + снимки + геофизика → многоканальный тензор → U-Net / SegFormer → маска → полигоны GeoJSON.

**Инструменты:** PDAL, rasterio, GDAL, RVT, geopandas, shapely, segmentation_models_pytorch, timm.

**Плюсы**
- Самый быстрый путь к первому сабмиту (1–2 недели).
- Зрелые библиотеки с чистыми лицензиями.
- Предобученные энкодеры, обучение помещается в 12 ГБ.
- Инференс легко укладывается в 30 мин, есть запас на TTA.
- Легко отлаживать визуально.

**Минусы**
- Все модальности на одной сетке: ресэмплинг теряет информацию (особенно геофизика).
- Точечные аномалии сегментация ловит плохо (мелкие, редкие, дисбаланс классов).
- Пропуск модальности на части территории ломает модель.
- Потолок качества ниже ансамблей.

**Сложность:** низкая-средняя
**Экспертные знания:** средние (какие визуализации рельефа выделяют курганы, валы, ямы)

**Возможные проблемы**
- Несовмещение растров: CRS, размер пикселя, сдвиги — тихие ошибки.
- Артефакты на краях тайлов → перекрытие и blending.
- Порог маски и мин. площадь полигона сильно влияют на метрику.
- Центр масс невыпуклого полигона может уйти за R_tolerance.

**Гибкость:** средняя (легко менять энкодер/каналы, новая модальность = переобучение)

---

### Стек 2. Модальные эксперты + фьюжн

**Суть:** отдельная модель на физический тип данных — рельеф, оптика, геофизика (+ детектор центров для точечных объектов). Объединение: голосование, взвешенные вероятности или мета-модель на признаках кандидатов.

**Инструменты:** всё из стека 1 + CenterNet-style heatmap-детектор, калибровка вероятностей, LightGBM/CatBoost для мета-модели, NMS по геометрии.

**Плюсы**
- Каждая модель работает в родном разрешении модальности.
- Устойчивость к пропускам данных.
- Естественное разделение работы на 4 человек.
- Подход призёров КОЗ №2.
- Фьюжн = ручка баланса precision / recall.
- Эксперта можно заменить, не трогая остальных.

**Минусы**
- Несколько моделей + постобработка → жёсткий учёт времени инференса.
- Больше кода и мест для ошибок, сложнее воспроизводимость.
- Фьюжн легко переобучить на публичную выборку.
- Мало сабмитов при большом числе комбинаций.

**Сложность:** средняя-высокая (в основном инженерная)
**Экспертные знания:** высокие (проявление объектов в магнитке и георадаре, доверие модальностям по классам)

**Возможные проблемы**
- Дубликаты: сдвинутые полигоны одного объекта от разных экспертов → нужен геометрический NMS.
- Разная калибровка моделей → сырые вероятности голосуют неправильно.
- Размер архива: несколько моделей укладываются, ансамбли из фолдов — уже вряд ли.
- Загрузка весов и чтение данных тоже входят в 30 мин.

**Гибкость:** высокая (лучше всего переносит обновления данных и метрики по ходу этапа)

---

### Стек 3. Нативная 3D-обработка облака + 2D

**Суть:** облако точек обрабатывается напрямую (Point Transformer v3 / KPConv / spconv), результат проецируется в растр и объединяется с 2D-веткой.

**Инструменты:** laspy, PDAL, Pointcept (PTv3), spconv / MinkowskiEngine, Open3D + стек 1.

**Плюсы**
- Нет потерь от растеризации: плотность, интенсивность, число отражений, структура под растительностью.
- Потенциально лучше находит слабовыраженные в рельефе объекты.
- Акцент КОЗ №3 — облака точек; может дать конкурентное преимущество.

**Минусы**
- 12 ГБ мало для обучения 3D-сетей на крупных облаках.
- Высокий риск не уложиться в 30 мин инференса.
- Разметка 2D → перенос меток на точки даёт шум.
- Сборка CUDA-расширений под Blackwell и офлайн-контейнер проблемная.
- У части 3D-репозиториев некоммерческие лицензии.
- Нет предобученных весов под археологию.

**Сложность:** высокая
**Экспертные знания:** очень высокие (3D DL + лидарная съёмка: классы точек, фильтрация земли, артефакты)

**Возможные проблемы**
- Месяц работы без прироста над стеком 1.
- Недетерминированность из-за сэмплинга точек.
- Сложно объяснить архитектуру на защите решения.

**Гибкость:** низкая (дорого менять, долго итерировать)

## 3. Роли для 4 человек

Сквозные обязанности во всех стеках:
- **Капитан** — связь с оргкомитетом, заявка, сабмиты, Декларация ИИ.
- Каждый ведёт свою часть в Декларации ИИ и готов объяснить свой код на защите.
- Единый репозиторий, фиксированные сиды, общий скрипт локальной метрики.

### Стек 1. Растровый baseline

| Роль | Зона ответственности | Ключевые артефакты |
|---|---|---|
| **A. Data / Geo** | LAS → DTM (PDAL), визуализации рельефа (RVT), совмещение всех растров, тайлинг с перекрытием | Пайплайн препроцессинга, кэш тайлов |
| **B. Model** | Архитектура, энкодеры, лоссы (Dice+Focal), аугментации, обучение с AMP | Веса, конфиги экспериментов |
| **C. Postprocess / Metric** | Маска → полигоны GeoJSON (EPSG:3857), порог, мин. площадь, центры масс; локальная метрика и валидационный сплит | Конвертер, скрипт метрики, отчёт по порогам |
| **D. MLOps / Инференс** (капитан) | Шаблон `inference/`, офлайн-окружение, замер времени и коэффициента 5070→4090, размер архива, сабмиты, лог экспериментов | Рабочий архив, таблица сабмитов |

### Стек 2. Модальные эксперты + фьюжн

| Роль | Зона ответственности | Ключевые артефакты |
|---|---|---|
| **A. Эксперт рельефа** | LAS → DTM + производные, модель по рельефу (развитие стека 1), признаки облака в каналах | Модель рельефа, её вероятности |
| **B. Эксперт оптики** | Аэро- и спутниковые снимки, историческая съёмка, совмещение разновременных данных, модель по оптике | Модель оптики, её вероятности |
| **C. Эксперт геофизики** | Магнитка и георадар, детектор точечных аномалий (heatmap/центры) | Детектор точек, её вероятности |
| **D. Фьюжн / MLOps** (капитан) | Калибровка, объединение, геометрический NMS, выходной GeoJSON, локальная метрика, бюджет времени на все модели, `inference/`, сабмиты | Слой фьюжна, рабочий архив |

Риск: роль D перегружена. После стабилизации экспертов часть MLOps забирает A.

### Стек 3. 3D + 2D

| Роль | Зона ответственности | Ключевые артефакты |
|---|---|---|
| **A. Point Cloud Data** | Чтение и фильтрация LAS, классификация земли, перенос 2D-разметки на точки, блоки для обучения | Размеченные блоки облака |
| **B. 3D Model** | PTv3 / KPConv, сборка под CUDA 12.8+, обучение в 12 ГБ, проекция результатов в растр | 3D-модель, растры вероятностей |
| **C. 2D ветка + фьюжн** | Стек 1 по рельефу и снимкам, объединение с проекцией 3D, полигоны, локальная метрика | 2D-модель, фьюжн, конвертер |
| **D. MLOps / Инференс** (капитан) | Офлайн-сборка 3D-зависимостей, контроль 30 мин и 2 ГБ, проверка лицензий, сабмиты | Рабочий архив, лицензионный реестр |

Риск: A и B блокируют друг друга. C обязан держать рабочий 2D-сабмит как страховку.
