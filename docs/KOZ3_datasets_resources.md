### 2.2. Формат LAS/LAZ

LAS — бинарный формат облаков точек (спецификация ASPRS, версии 1.2–1.4). LAZ — его сжатая версия. Структура: заголовок (границы, число точек, масштаб и смещение координат, CRS в VLR) + записи точек.

Что есть в каждой точке (зависит от Point Data Record Format):
- `X, Y, Z` — целые, умножаются на `scale` и прибавляется `offset` из заголовка;
- `intensity` — сила отражённого сигнала;
- `return_number`, `number_of_returns` — номер отражения и их количество (первое отражение — верх кроны, последнее — часто земля);
- `classification` — класс точки по стандарту ASPRS: 2 = земля, 3–5 = растительность, 6 = здания, 9 = вода. **Классификация может отсутствовать или быть грубой — проверять**;
- `scan_angle`, `gps_time`, иногда RGB.

Чтение через `laspy`:

```python
import laspy, numpy as np

with laspy.open("tile.las") as f:
    hdr = f.header
    print(hdr.point_count, hdr.mins, hdr.maxs, hdr.point_format)
    # чанками, чтобы не грузить всё в память
    for chunk in f.chunk_iterator(2_000_000):
        xyz = np.vstack([chunk.x, chunk.y, chunk.z]).T   # уже с scale/offset
        cls = np.asarray(chunk.classification)
        inten = np.asarray(chunk.intensity)
        nret = np.asarray(chunk.number_of_returns)
```

Для LAZ нужен бэкенд: `pip install laspy[lazrs]`.

**Подводные камни:**
- CRS может быть не записан в VLR — брать из документации к данным;
- плотность точек неравномерна (полосы траекторий), под водой и плотной застройкой — дыры;
- «земля» по классификации может включать низкую растительность или, наоборот, срезать насыпи;
- интенсивность не калибрована между полётами, использовать только после нормализации в пределах файла.

**Первая инвентаризация каждого файла:** плотность точек/м², гистограмма классов, гистограмма интенсивности, доля непервых отражений, bbox. Это скажет, с чем мы имеем дело, раньше, чем модель.

### 2.3. Формат GeoTIFF

Растр + геопривязка внутри тега: affine-трансформация (`transform`) и CRS. Ключевые поля через `rasterio`:

```python
import rasterio

with rasterio.open("mag.tif") as src:
    print(src.crs, src.res, src.bounds, src.count, src.dtypes, src.nodata)
    arr = src.read()          # (bands, H, W)
    T = src.transform         # affine: пиксель → координаты
    x, y = T * (col + 0.5, row + 0.5)   # ЦЕНТР пикселя
```

**Подводные камни:**
- `nodata` может быть не выставлен, а дыры закодированы нулём или -9999;
- разные слои — разные CRS (UTM, локальная, EPSG:3857). Приводить к одной сетке явно;
- координата пикселя — угол или центр? В affine по умолчанию угол; при переводе масок в полигоны ошибка на полпикселя систематически съедает матчи;
- геофизические визуализации могут быть уже нормализованы и обрезаны по перцентилям — это потеря информации, сырые значения лучше;
- у исторических снимков привязка часто грубая, сдвиги в метры. Проверять кросс-корреляцией с современным слоем.

### 2.4. GeoJSON и EPSG:3857

GeoJSON — текстовый JSON с геометриями. Регламент требует EPSG:3857 (Web Mercator, метры, но **не истинные**: масштаб искажён и растёт с широтой). Следствия:
- расстояния для R_tolerance считаются в координатах 3857, а не в реальных метрах. Наша метрика должна делать ровно так же, как официальная;
- площади полигонов в 3857 тоже искажены — для фильтра по минимальной площади это не важно, если порог подбирается по метрике, а не по «настоящим» метрам.

Минимальный писатель без зависимостей:

```python
import json

def write_geojson(path, dets):
    fc = {"type": "FeatureCollection",
          "crs": {"type": "name", "properties": {"name": "EPSG:3857"}},
          "features": [{
              "type": "Feature",
              "geometry": {"type": "Polygon", "coordinates": [d.ring]},
              "properties": {"class": d.cls, "score": float(d.score)}
          } for d in dets]}
    json.dump(fc, open(path, "w"))
```

Точный формат выходного файла (имена полей, нужен ли score, порядок координат) взять из **примера выходного файла на платформе** и сверять валидатором перед каждым сабмитом.

### 2.5. Как устроены объекты в каждой модальности

**Рельеф (DTM):**
- курган — округлая выпуклость 5–40 м в диаметре, высота 0,3–5 м; хорошо видна на SLRM и positive openness;
- вал/ров — вытянутые пары «гребень + впадина»; negative openness выделяет рвы;
- городище — платформа с валами по периметру, десятки–сотни метров;
- ловушки: современные насыпи, дренаж, лесные дороги, воронки от снарядов.

**Оптика:**
- cropmarks — различия в росте растений над подземными структурами, видны в определённый сезон;
- soilmarks — цвет почвы на распашке;
- исторические снимки показывают то, чего уже нет.

**Магнитометрия:**
- аномалия часто выглядит как **дипольная пара «плюс–минус»**, центр объекта смещён относительно геометрического центра пары. Для матчинга по центру масс это критично;
- полосовые артефакты от хода оператора — удалять до подачи в модель.

**Георадар:**
- точечный объект на радарограмме даёт **гиперболу**; на горизонтальных срезах (time-slices) — пятно;
- нам дают `.tif`-срезы, то есть уже проекцию. Скорее всего несколько срезов по глубине — использовать как каналы.

## 4. Метрика: как считать и как проверить, что мы считаем правильно

### 4.1. Что известно из регламента

- Полигон↔полигон: способ матчинга не указан явно (вероятно IoU или пересечение — ждём код с платформы).
- Полигон↔точка: **центр масс предсказанного полигона** в пределах `R_tolerance` от GT-точки, расстояние евклидово в EPSG:3857.
- Успешное участие = метрика > 0.
- Формула не приведена; код расчёта дадут на платформе в начале квалификации.

### 4.2. Литература по метрикам для археологической детекции

| Источник | Что взять |
|---|---|
| Fiorucci et al., 2022, «Deep Learning for Archaeological Object Detection on LiDAR: New Evaluation Measures and Insights», Remote Sensing 14(7):1694 | Centroid-based и pixel-based метрики. Предсказание — TP, если его центроид попал в GT; два предсказания в одном GT — один TP и один FP. **Это очень похоже на нашу метрику** |
| Код к статье | https://github.com/IIT-CCHT/esa-cls-evaluation-measures — референсная реализация, можно сверять свою |
| Archaeoscape (NeurIPS 2024) | Бенчмарк сегментационных моделей на археологии, протокол сплита по участкам |

### 4.3. Как проверить, что наша метрика верна

Тесты, которые должны быть зелёными до первого сабмита:

1. **Идеал.** Предсказание = GT → метрика максимальна.
2. **Пусто.** Нет предсказаний → recall 0, метрика 0 (или минимум по формуле).
3. **Всё.** Один полигон на всю территорию → recall по полигонам может быть высоким, precision около 0; проверить, что формула это штрафует.
4. **Сдвиг.** GT-точка + полигон с центром масс на расстоянии `R_tolerance − ε` → TP; `R_tolerance + ε` → FP + FN.
5. **Дубли.** Два полигона на одну GT-точку → ровно один TP.
6. **Невыпуклый.** Подковообразный полигон, у которого центр масс вне полигона → проверить, что считаем центр масс, а не центр bbox.
7. **CRS.** Тот же набор в UTM и в 3857 → расстояния отличаются; убедиться, что метрика работает строго в 3857.
8. **Сверка с официальным кодом** сразу после его публикации: одинаковый вход → одинаковый результат до 10 знаков.

### 4.4. Как понять, что модель «примерно верна» до реальных данных

- **Синтетика:** на игрушечном датасете с известными объектами метрика должна быть близка к 1. Если нет — баг в пайплайне, а не в модели.
- **Суррогат с реестром:** на AHN + Archis по курганам Велюве ожидать recall 0.6–0.8 по литературе (WODAN давал около 70 % на неслучайной выборке и заметно ниже на случайной). Если у нас 0.2 — что-то сломано; если 0.99 — утечка.
- **Кросс-регион:** обучить на одном регионе, проверить на другом. Падение неизбежно, но не до нуля.
- **Разбор ошибок глазами:** 20 случайных FP и 20 FN на hillshade. Половина FP на суррогате обычно оказывается реальными неразмеченными объектами.
