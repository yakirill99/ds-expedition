# [Оракул] Потеря 76% эталона до модели: три бага деления + инструменты диагностики

**Дата:** 2026-11-11
**Ветка:** `test/geo-pr55`
**Триггер:** разбор прогона `runs/n3_long` (180 эпох): oracle f1 **0.386** вместо ~1.0,
recall 0.244 — пайплайн терял 1147 из 1518 эталонных объектов ещё до модели.
Локальный val f1 застрял на ~0.015 при train dice 0.025.

**Вход:** `src/expds/post/vectorize.py`, `src/expds/train.py`, конфиг `night2.yaml`
(= конфиг n3_long), разбор n3_long.
**Выход:** починенный post-пайплайн, гейт оракула + early stopping в train,
инструменты `scripts/oracle_diag.py` и `scripts/audit_channels.py`,
конфиг ретрейна `configs/night3.yaml`, регрессионные тесты.

---

## 1. Найденные баги (все три — причина провала оракула)

### Баг №1 (главный): hm не доходил до сег-полигонов — деление было мёртвым кодом

`postprocess()` вызывал `seg_to_polygons(probs[i], ...)` **без heatmap**.
Вся машинерия деления слитых объектов (`_split_by_peaks`, watershed) была
написана, протестирована юнит-тестами — и **ни разу не выполнялась в бою**:
без hm каждый компонент = один полигон. Соприкасающиеся курганы
(плотные поля на 130/145/150_Курганы_*) склеивались в один блоб =
1 TP + N-1 FN. Это в точности профиль n3_long: precision 0.914 (потери
не портили объекты — они исчезали), recall 0.244.

**Фикс:** `postprocess` передаёт `hm=probs[k + i]` в seg-ветку.

### Баг №2: плато пиков — один объект давал 4 «пика»

Центроида полигона часто попадает между пикселями (`col = 29.5`), тогда
гауссиана hm имеет **плато 2x2 со значением ровно 1.0**, а условие
`hm >= maximum_filter(hm)` (сравнение нестрогое) оставляет ВСЕ пиксели
плато как «пики». Дальше Voronoi по 4-8 «пикам» делил один объект на
сектора с IoU ~0.25 — детекция не проходила матчинг. Измерено на
контролируемой паре: 8 «пиков» вместо 2 объектов, 8 частей по IoU 0.25.

**Фикс:** `_hm_peaks()` дедуплицирует плато (8-связные компоненты маски
пиков → один представитель: максимум hm, при равенстве минимальный
(row, col) — детерминированно).

### Баг №3: глобальный гейт watershed — один мелкий компонент отключал деление всем

Старый `split_touching` запускал watershed по глобальному условию
`len(peaks) > n_components` с порогом `threshold_abs = min_distance/2 = 2.0`.
Пики мелких объектов (r < 2 px) порог не проходили → на rebuilt-данных
78 пиков < 87 компонент → **watershed молча не запускался ни разу**.
Кроме того, watershed по distance transform резал пары кругов разных
радиусов вглубь малого (IoU 0.46 < 0.5).

**Фикс:** деление покомпонентное, по рельефу самой hm: маркеры = пики
(со слиянием ближних `split_min_distance_px`), террейн = −hm, граница
проходит по седлу между гауссианами (= биссектор центров для равных сигм).
Для кругов 10px+6px с перекрытием 4px: IoU частей с объектами 0.85/0.86
(было 0.46). Флаг `split_touching=False` сохраняет старое Voronoi-поведение
(с починенной дедупликацией пиков).

| night2 до патча | 71 | 0 | 24 | 1.000 | 0.747 | 0.855 |

## 5. Порядок запуска на реальных данных (перед ретрейном)

```bash
git pull --ff-only origin test/geo-pr55

# 1. Каналы: где «доступно=3 из 31» и чего именно не хватает
uv run python scripts/audit_channels.py --config configs/night3.yaml
# участки без mean_z/z_std дособрать стеком (tools/rebuild_relief_from_dtm.py)

# 2. Оракул на val-участках (цель: f1 -> 1.0; если ниже — см. причины по стадиям)
uv run python scripts/oracle_diag.py --config configs/night3.yaml --sweep

# 3. Если оракул >= 0.95 — короткий ретрейн (гейт сам не пустит при < 0.95)
uv run python scripts/train.py --config configs/night3.yaml
```

Ожидание по метрикам после фикса: oracle f1 на rebuilt-val должен подняться
с 0.386 к ~0.95+; всё, что останется ниже, теперь видно по стадиям
(«слияние» → пост-параметры, «valid/nodata» → дыры съёмки, «min_area» →
порог площади). Early stopping остановит ретрейн, когда val-ключ перестанет
расти (в n3_long сэкономило бы ~2.9 ч), и каждый чекпойнт выбирается по
`checkpoint_key`, а лог per-class показывает, какие типы объектов растут.
