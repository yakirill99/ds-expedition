# Патч-отчёт: oracle gate не должен блокировать обучение на GT «вне сетки» и в единицах, которых не знает платформа

Коммиты: `src/expds/eval/metric.py`, `src/expds/eval/oracle.py`, `src/expds/train.py`,
`src/expds/features/grid.py`, `configs/night3.yaml`, `configs/yd130_oracle.yaml`,
`scripts/oracle_diag.py`, `tests/test_offgrid_coverage.py` (новый).
Ветка: `test/geo-pr55`.

## Симптом

`scripts/train.py --config configs/night3.yaml` падает до обучения:

```
RuntimeError: oracle gate: f1 0.791 < порога 0.95 — пайплайн теряет эталон до модели
(tp 1055 fp 93 fn 463). Обучение даст ложную метрику.
oracle по классам: fortifikatsii f1 0.000 p 0.000 r 0.000 (tp 0 fp 9 fn 69)
oracle по классам: kurgany_povrezhdennye f1 0.790 p 0.917 r 0.693 (tp 745 fp 67 fn 330)
```

Плюс 5 warning'ов «Канал ... отсутствует, заполняем нулями» на каждый участок.

## Диагноз: три независимые причины, все — не ошибки модели

**1. 456 из 461 FN оракула — GT, целиком выпавшие из растра** (аудит
`docs/issues/07-grid-coverage.md`, `scripts/grid_coverage_check.py`):
036_Тимерево 312/885, 066_Московиты 67/69, 008_Герите 36/45,
102_Гнёздово_Заольшанская 20/136, 056_Фалхан 17/53. bbox разметки шире bbox
растровых данных. Ни одна модель не может детектировать объект, которого нет
на растре, — но старый оракул и val-метрика считали каждый такой объект FN и
топили гейт. Поправка `ef98ec5` касалась только точечных классов (NMS), а в
val-сплите Point 0 — полигонные «вне сетки» никуда не делись. Цифра «69 FN
fortifikatsii» совпадает с «GT 69, вне сетки 67» участка 066_Московиты.

**2. Локальный матчинг был строже платформенного.** Гейт мерил потолок в
единицах строгого IoU >= 0.5, а платформа (ТР КОЗ-3, Приложение 4,
`vendor/organizers/compute_metrics.py`) засчитывает GT при
cov = area(P∩G)/min(area(P), area(G)) >= 0.5 И представительской точке pred
внутри GT. Watershed-доли слитых курганов и стены, обрезанные контуром,
дают IoU 0.4-0.5, но cov ~1.0 — платформа их засчитывает, локальный гейт
браковал и запрещал обучение на «неправильных» с его точки зрения данных.

**3. Выборка пересечения полигонов «мазала» тонкие контуры.** `polygon_iou`
клала равномерную сетку 128×128 по bbox пары. Стена 1-2 px шириной (валы,
рвы) под 45°: вероятность попадания точки сетки внутрь контура ~ ширина /
сторона bbox — почти ноль. Пересечение оценивалось нулём при честном
совпадении контуров; даже совпадающие стены получали IoU = 0. Отсюда
`fortifikatsii tp 0` на оставшихся в сетке объектах.

## Что изменено

### `src/expds/eval/metric.py`

- `EvalConfig.match_mode: "iou" | "coverage"` (по умолчанию `iou` — старое
  поведение) и `cov_thr: float = 0.5`. В режиме `coverage` качество пары —
  cov по min-площади, при `cov >= cov_thr` дополнительно требуется
  представительская точка pred внутри GT (правило ТР КОЗ-3). Точечный
  матчинг не изменился.
- `representative_point(rings)` — аппроксимация
  `shapely.representative_point()` без shapely: сетка 32×32 по bbox, точка
  внутри контура, ближайшая к центроиду. Считается один раз на pred.
- `_pair_intersection` переписана на **сканлайн-выборку**: точки берутся из
  интервалов пересечения горизонталей с полигоном меньшей площади — любая
  точка лежит внутри по построению, независимо от толщины/ориентации
  контура; дыры учитываются even-odd по всем кольцам. Это чинит IoU/cov
  для всех режимов, не только coverage.
- Новое поле `EvalConfig.ignore_offgrid: bool = False` (см. ниже).

### `src/expds/eval/oracle.py`

- При `eval.ignore_offgrid=true` GT без единого пикселя растеризации
  (`obj_mask_raw is None`) исключаются из матчинга: не считаются FN, гейт
  их не видит. В отчёте они остаются: новое поле `OracleReport.gt_offgrid`
  и причина «вне сетки» в `reasons`. Частично вошедшие объекты остаются в
  метрике (при coverage модель, увидевшая часть объекта, получает cov по
  min-площади — честно и платформенно).

### `src/expds/train.py`

- `_score` (общий путь oracle + валидации) при `eval.ignore_offgrid`
  фильтрует GT: `_offgrid_keep_mask` строит след сетки участка в CRS
  метрики (16×16 точек границы, bbox выпуклой оболочки — ничего внутреннего
  не теряется при любом переходе CRS) и оставляет объекты, пересекающие
  его (точкам — запас r_tol, с пересчётом «meters» как в матчере).
- `fit` один раз печатает сводку по val-участкам: сколько GT исключено как
  «вне сетки» — новые семантики метрики видны в логе, а не спрятаны.
- Сообщение гейта дополнено подсказкой про `eval.ignore_offgrid`.

### `src/expds/features/grid.py`

- Warning'и отсутствующих каналов слиты в одну строку на участок:
  `Каналы отсутствуют, заполняем нулями (mask=False): non_first_return_ratio, ...`.
  Это **не ошибка**: конфиг night3 просит 31 канал (лидар-облако, магнитка,
  rgb), на участках без облака/магнитки соответствие заполняется нулями по
  дизайну (`channel_mask=False`), модель это переживает.

### `configs/night3.yaml`, `configs/yd130_oracle.yaml`

```yaml
eval:
  match_mode: coverage     # метрика в единицах платформы (ТР КОЗ-3)
  ignore_offgrid: true     # GT вне растра участка не считаются FN
```

`train.oracle_gate: 0.95` остался без изменений: на исправленной семантике
гейт проходится с запасом (см. ниже).

## Что это НЕ чинит (известный потолок)

Пересекающиеся СЕТКИ стен (крест-накрест): y_seg даёт один компонент сети,
hm — гауссианы в центроидах; watershed делит сеть по евклидовой близости к
центрам, доля накрывает свою стену частично (cov 0.3-0.7). Ни маска, ни
heatmap не несут информации о принадлежности ветвей сети — это потолок
постобработки, а не ошибка матчинга. Случайные углы стен в синтетике дали
f1 fortifikatsii ~0.3-0.6 на такой сети; почти параллельные линии валов
(реальные валы/рвы) проходят.

## Как пользоваться

```bash
cd ~/ds-expedition
git pull origin test/geo-pr55
# контроль перед обучением (печатает «вне сетки (исключены из метрики)»):
uv run python scripts/oracle_diag.py --config configs/night3.yaml
# обучение:
uv run python scripts/train.py --config configs/night3.yaml
```

Ожидаемо в логе: строки «<участок>: GT N, вне сетки M — исключены из
метрики и гейта», затем oracle val f1 ~0.95-0.97 (точное число зависит от
доли пересечённых сеток стен на val-участках) — и обучение начинается.
Если oracle всё же < 0.95: смотреть `oracle_diag.py` — строки «причины FN»;
«вне сетки (исключены)» теперь видны отдельно от реальных потерь пайплайна.
