# КОЗ №3: роадмап команды, роли и зоны ответственности

Стратегия: **стек 1 (растровый baseline) → стек 2 (модальные эксперты + фьюжн)**.
Стек 1 не выбрасывается при миграции — он становится экспертом по рельефу (E1) внутри стека 2. Поэтому с первого дня пишем код так, будто эксперта будет три.

Команда: **5 человек**. Работаем в одном репозитории, без параллельных веток «кто-то делает стек 1, кто-то стек 2».

## 1. Роли

Пять ролей. Каждая — это **зона ответственности**, а не «человек, который пишет только это». Ревью делают все.

### Роль 1. Data / Geo — «рельеф и геометрия»

**Кратко:** превращает сырой лидар в качественные признаки и отвечает за то, чтобы все слои лежали в одной системе координат без сдвигов.

**Что именно требуется**

1. **Чтение лидара.** Реализовать чанкованное чтение LAS/LAZ (через `laspy`), достать XYZ, интенсивность, номер и количество отражений, класс точки. Написать инвентаризацию файла: границы, плотность точек на м², гистограммы интенсивности и классов, доля непервых отражений. Без этого непонятно, с какими данными вообще работаем.

2. **Фильтрация земли.** Написать свой прогрессивный морфологический фильтр: минимальная поверхность по ячейкам → морфологическое открытие с растущим окном → порог по наклону → итеративное досыпание точек. Обязательно **два режима**: строгий (убирает растительность и здания) и мягкий (сохраняет насыпи). Главная опасность — агрессивная фильтрация срезает сами курганы, то есть удаляет объект поиска. Проверять визуально на участке с известным курганом.

3. **Построение DTM.** Биннинг точек земли в регулярную сетку (`np.add.at` / `binned_statistic_2d`), статистики по ячейке (min, mean, count), заполнение пустых ячеек своей интерполяцией (IDW по KD-дереву). Контроль артефактов: полосы от траекторий съёмки, дырки под водой и плотной застройкой.

4. **Производные рельефа.** Это главный источник качества всей рельефной ветки. Написать своими руками:
   - hillshade с нескольких азимутов (метод Horn для градиентов);
   - slope и aspect;
   - SLRM на трёх масштабах: `DTM − gaussian_blur(DTM, σ)`, σ ∈ {2, 8, 32} px;
   - positive и negative openness (поиск максимального угла обзора по N направлениям);
   - sky-view factor;
   - локальную кривизну (вторые производные);
   - растровые признаки прямо из облака: плотность точек, средняя интенсивность, доля непервых отражений.
   
   Реализация на torch даёт возможность считать признаки на GPU в даталоадере и не хранить их на диске.

5. **Общая сетка и выравнивание.** Задать `Grid` (CRS, размер пикселя, extent), написать свой ресэмплер (`scipy.ndimage.map_coordinates`), привести все слои к одной сетке. Отдельно — **утилита проверки совмещения**: кросс-корреляция пары слоёв, вывод сдвига в пикселях. Сдвиг на 2–3 пикселя между модальностями — типичная причина, по которой хорошая модель даёт плохую метрику, и находить его надо в сентябре, а не в ноябре.

**Зона ответственности:** `src/io/las.py`, `src/prep/ground.py`, `src/prep/dtm.py`, `src/prep/relief.py`, `src/prep/align.py`.

**При миграции в стек 2:** становится владельцем эксперта **E1 (рельеф)** — то есть модели, выросшей из baseline.

**Критерий «работа сделана хорошо»:** любой участник может взять сырой `.las` незнакомого участка, запустить одну команду и получить набор чистых признаков в общей сетке.

### Роль 2. Model — «модели и обучение»

**Кратко:** архитектура сетей, лоссы, аугментации, режим обучения в 12 ГБ.

**Что именно требуется**

1. **Своя сегментационная сеть.** U-Net или FPN на чистом PyTorch: свои блоки, skip-соединения, головы. Принципиальное требование — **число входных каналов задаётся конфигом**, а не хардкодом, потому что набор признаков будет меняться каждую неделю. Энкодер можно взять из `timm` (Apache 2.0), но с `pretrained=False` на платформе — интернета там нет, веса должны лежать в архиве.

2. **Лоссы.** Комбинация Dice + Focal для сегментации: объекты редкие, дисбаланс огромный, обычный BCE даёт пустые предсказания. Добавить веса пикселей (граница объекта важнее середины) и маску игнорирования вокруг объектов, чтобы не штрафовать за «почти попал».

3. **Аугментации.** Писать свои, потому что гео-данные требуют идентичного преобразования всех слоёв и таргетов одновременно: повороты на 90°, отражения, небольшие сдвиги, шум, сдвиг гистограмм по каналам. Отдельно — **случайное выключение целых групп каналов**: это заранее готовит модель к работе при отсутствующей модальности, что понадобится в стеке 2.

4. **Обучение под 12 ГБ.** AMP (mixed precision), gradient checkpointing, накопление градиента вместо большого batch, подбор размера тайла. Фиксация сидов и проверка воспроизводимости: два запуска с одним сидом должны давать один результат.

5. **Дисциплина экспериментов.** Каждый прогон — запись в лог: хэш коммита, конфиг, метрика на валидации, время обучения, вывод. Без этого через две недели никто не вспомнит, почему выбрали именно эти параметры.

6. **Позже — heatmap-детектор.** Для точечных объектов (CenterNet-подход): гауссовы таргеты, penalty-reduced focal loss, извлечение центров через локальные максимумы. Понадобится в стеке 2 для геофизики, но заложить интерфейс стоит заранее.

**Зона ответственности:** `src/models/`, `src/data/augment.py`, скрипты обучения.

**При миграции в стек 2:** помогает поднять E2 (оптика), передаёт наработки по heatmap для E3.

**Критерий:** смена набора входных признаков не требует правок в коде модели — только в конфиге.

### Роль 3. Post / Vector — «выход и разбор ошибок»

**Кратко:** превращает вероятности в геометрию, которую засчитает метрика, и объясняет команде, почему метрика не растёт.

**Что именно требуется**

1. **Векторизация.** Порог → контуры (marching squares) → упрощение (свой Дуглас-Пекер) → перевод пиксельных координат в EPSG:3857 через affine. Аккуратно с тем, что координата пикселя — это его центр, а не угол: систематическая ошибка в полпикселя стабильно съедает часть матчей.

2. **Контроль центра масс.** Точечный объект засчитывается, если **центр масс нашего полигона** попал в радиус R_tolerance от GT-точки. Следствия: у невыпуклых и подковообразных предсказаний центр масс может оказаться снаружи полигона — такие случаи надо детектировать и заменять геометрию на круг вокруг взвешенного центра вероятности. Для точечных детекций сразу строить небольшой правильный многоугольник вокруг пика.

3. **Подбор порогов.** Порог вероятности, минимальная площадь полигона, степень упрощения — всё это подбирается по локальной метрике, а не на глаз. Держать в конфиге, никаких магических констант в коде. Смещение в сторону recall: археологам полнота важнее точности.

4. **Geo-NMS.** Дедупликация: сортировка по score, подавление по IoU полигонов или по расстоянию между центрами (порог привязан к R_tolerance), пространственный индекс через `shapely.STRtree`. В стеке 2 это станет критично: разные эксперты дают сдвинутые предсказания одного объекта.

5. **Writer и валидатор.** Запись GeoJSON через обычный `json` — формат текстовый, лишние зависимости не нужны. Отдельно — **валидатор**, сверяющий наш выходной файл с примером с платформы до сабмита. Неверный формат = сожжённая попытка из десяти.

6. **Разбор ошибок.** Самая ценная часть роли. Инструмент, который берёт предсказания и GT и отвечает: какие классы теряем, какого размера объекты пропускаем, где FP кучкуются, на каких участках метрика проседает. Из этого рождаются гипотезы для следующих сабмитов.

**Зона ответственности:** `src/post/`, `src/io/vector.py`, `src/eval/errors.py`.

**Критерий:** на идеальном (совпадающем с GT) предсказании наш пайплайн выдаёт максимум метрики. Если нет — теряем баллы на выходе, а не на модели.

### Роль 4. MLOps / Инференс — капитан

**Кратко:** отвечает за то, что решение запускается на платформе, укладывается в лимиты и вовремя подаётся. Плюс вся коммуникация с оргкомитетом.

**Что именно требуется**

1. **Организационное (приоритет №1 в сентябре).** Регистрация всех на платформе через Leader ID, создание команды, рассылка инвайтов, **командная заявка на cabinet.nti.one до 30 сентября**. ФИО и название команды должны совпадать в обеих системах. Всё общение с оргкомитетом идёт через капитана.

2. **Окружение.** PyTorch с CUDA 12.8+ под Blackwell (5070), пины версий в `requirements.txt`, воспроизводимая сборка. Проверка, что всё поднимается **без интернета** — на платформе сети нет.

3. **Коэффициент 5070 → 4090.** Замерить на одинаковой модели и тайлах, получить число, на которое умножаются все локальные замеры. Довести до всех: локальный прогон ≤ 15 минут.

4. **Профилировщик.** Таблица по стадиям на каждом прогоне: чтение LAS, DTM и признаки, чтение растров, инференс, сшивка, векторизация, запись. Когда бюджет начнёт поджимать, без этой таблицы оптимизировать будет нечего.

5. **Сборка решения.** Папка `inference/` с entrypoint по требованиям платформы, скрипт `make submission` от чистой копии репозитория до готового архива. Контроль размера ≤ 2 ГБ и отсутствия в архиве данных выборок — платформа отклоняет такие решения автоматически.

6. **Управление сабмитами.** 3 успешных запуска в сутки, 10 попыток всего. Каждый сабмит — проверка одной гипотезы. Таблица: дата, коммит, гипотеза, локальная метрика, метрика платформы, вывод. Один запуск в день держать в резерве на случай ошибки формата.

7. **Комплаенс.** Реестр лицензий всех зависимостей и сторонних данных. `DECLARATION_AI.md` ведётся с первого коммита — по регламенту нужна полная декларация использования ИИ-инструментов, а расхождение с фактической структурой кода ведёт на защиту решения.

**Зона ответственности:** `inference/`, `tools/`, `src/utils/profiler.py`, вся коммуникация и документы.

**Критерий:** в любой момент можно собрать архив с нуля и получить валидный результат за понятное время.

### Роль 5. Каркас / Валидация

**Кратко:** держит архитектуру пайплайна и отвечает за то, что локальная метрика не врёт. Именно эта роль делает миграцию в стек 2 дешёвой.

**Что именно требуется**

1. **Контракты данных.** Спроектировать и защищать `DataSpec`, `Grid`, `Layer`, `Sample`, `Detection`. Правила, которые нельзя нарушать: ни один модуль не хардкодит имена файлов и число каналов; отсутствие модальности — штатная ситуация, а не исключение; разрешение и размеры окон задаются в метрах, а не в пикселях. Ревьюит любой PR, меняющий сигнатуры между модулями.

2. **Конфигурация.** `dataset.yaml` как единственное место, где живёт знание о конкретном датасете. Смена датасета = смена YAML, ноль правок в коде. Свои dataclass + валидация, без Hydra и прочей магии.

3. **Генератор синтетики.** `tools/make_synthetic.py`: синтетический DTM с гауссовыми «курганами», вытянутыми «валами» и «рвами», RGB-слой с шумом, магнитка с дипольными парами, георадар с гиперболами, GeoJSON-разметка. Генерация < 1 минуты. Это позволяет писать и тестировать весь пайплайн, не дожидаясь реальных данных 1 октября, и даёт end-to-end тест в CI.

4. **Суррогатные датасеты.** Подобрать открытый лидар с рельефными объектами и открытые снимки, с проверенной лицензией. Прогнать на них весь пайплайн, сменив только YAML. **Это главный тест архитектуры:** если понадобилась правка кода — баг проектирования, чиним немедленно.

5. **Метрика.** Своя реализация матчинга по регламенту (полигон↔полигон по IoU, полигон↔точка по центру масс). Когда на платформе появится официальный код — сверить, добавить тест на совпадение, дальше держать свою как быструю, официальную как эталон.

6. **Валидационный сплит.** Разбиение **по территориям**, а не случайное: соседние тайлы перекрываются, случайный сплит даёт утечку и красивую локальную метрику, которая рассыпается на платформе. Сплит документирован, все используют один и тот же.

7. **Тайлер и сшивка.** `TileIndex` с оконным чтением, сэмплер с балансировкой позитивов (объекты редкие, случайные тайлы пустые в 95% случаев), перекрытие ≥ 25%, сшивка с весовым окном без швов.

8. **Позже — калибровка и фьюжн.** Как только у стека 1 есть стабильная метрика: температурная шкала для калибровки вероятностей и слой фьюжна (взвешенное среднее с перенормировкой по доступным модальностям + режим k-of-n). Включается, когда появится второй эксперт.

**Зона ответственности:** `src/spec.py`, `src/data/tiles.py`, `src/eval/metric.py`, `src/fusion/`, `tools/make_synthetic.py`, `tests/`.

**Критерий:** прогон на трёх датасетах (синтетика, суррогат, конкурс) без единой правки кода.

### Фаза 6. Точка ветвления → стек 2 — ~25 октября

**Условие входа (проверяется явно, не на ощупь):**
- стек 1 даёт устойчивую ненулевую метрику на платформе;
- полный прогон укладывается во время с запасом;
- локальная и платформенная метрика согласованы.

Пока хотя бы одно не выполнено — **не ветвимся**. Иначе есть риск остаться вообще без работающего решения.

**После входа:**

| Кто | Новая задача |
|---|---|
| Data/Geo | Владелец **E1 (рельеф)** — продолжает улучшать baseline как эксперта |
| Model | Поднимает **E2 (оптика)**: аэро, исторические снимки, спутник |
| Post/Vector | Разбор ошибок фьюжна, geo-NMS между экспертами, доводка выхода |
| Каркас | **E3 (геофизика)**: heatmap-детектор аномалий + калибровка + фьюжн |
| MLOps | Бюджет времени на три модели, размер архива, сабмиты |

**Правило включения фьюжна:** он подключается, когда есть **минимум два эксперта с ненулевой метрикой**. До этого момента фьюжн не улучшает ничего, а только усложняет отладку.

**Контроль отката:** рабочая версия стека 1 всегда остаётся собираемой отдельным конфигом. Если фьюжн не даёт прироста к началу ноября — сабмитим стек 1 и не жалеем.

## 3. Правила совместной работы

1. **Один репозиторий.** Никаких параллельных веток «стек 1 отдельно, стек 2 отдельно».
2. **Контракты неприкосновенны.** PR, меняющий сигнатуру между модулями, ревьюит роль Каркас.
3. **Каждый понимает чужой код.** По регламенту на защите отвечает вся команда. Ревью — не формальность, а страховка от дисквалификации.
4. **Никаких магических констант.** Все пороги, σ, масштабы — в конфиге.
5. **Три датасета в CI.** Синтетика, суррогат, конкурсные данные. Ломается любой — PR не мержится.
6. **Лог экспериментов обязателен.** Коммит, конфиг, метрика, вывод.
7. **Декларация ИИ ведётся с первого дня**, а не собирается в декабре по памяти.
