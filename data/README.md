# Реестр данных

Всё, что тяжелее ~5 МБ, живёт на Яндекс Диске. В git — только этот реестр.
Скачать всё: `make data`. Одна позиция: `uv run python scripts/fetch_data.py --only <id>`.

Пути в таблице — куда файл ляжет относительно корня репо (в `.gitignore`).

## Пакетная обработка

Все лидарные участки обрабатываются одной командой:

    uv run python scripts/process_sites.py --data-dir data/raw

Скрипт находит все папки с UTM.json, для каждой патчит `configs/default.yaml`
и запускает полный пайплайн. Результат — `data/cache/<name>/{layers,samples}/`.

Только конкретные участки:

    uv run python scripts/process_sites.py --data-dir data/raw --only 006 017

Пропустить участки:

    uv run python scripts/process_sites.py --data-dir data/raw --skip 048

## Правила
- Добавил файл на диск — добавил строку сюда в том же PR, что и код, который его использует.
- Имя файла на диске = имя в колонке «Путь». Не переименовывать.
- Версии не перезаписываем: новая версия — новая строка (`baseline_ckpt_v0.2`).
- Ссылка должна быть публичной («Поделиться» → «Скопировать ссылку»).

## TODO: мульти-UTM из «Указание UTM-зон»

В регламенте хакатона упомянута таблица `Указание UTM-зон`: для каждой
папки площадки своя UTM-зона (36N, 37N, WGS84 и т.п.). Сейчас CRS
определяется автоматически:

1. LAS header (если у лидара прописан CRS) — приоритет.
2. `UTM.json` в папке участка.
3. `configs/default.yaml → crs.source` (fallback с warning).

Если организаторы дадут таблицу зон как отдельный файл — добавим её
загрузку в `inventory_site` и приоритет: **таблица > LAS header >
UTM.json > config**. Пока таблицы нет — не блокирует: на наших участках
UTM.json есть.

## TODO: семантика Li-карт и SpOr

Li_c/ch/g/i (3 канала, uint8) и SpOr (3 канала + alpha=255) — назначение
каналов не расшифровано. Спектральные индексы на них не строятся
(NDVI требует NIR, которого физически нет). Ждём расшифровку от
организаторов — тогда сможем использовать эти модальности как признаки.
